# v0.4.0 — Admin panel and security

> **The admin panel can now edit all site content, and the auth endpoints, public inputs and workflows have stricter limits.** **65 commits** since v0.3.0. 3 migrations. The release adds the content screens, password reset pages, a visit counter, the SEO foundation and a set of security checks. The live site stays out of search indexes until 1.0.0.

This release builds the admin side of the site on the public site from v0.3.0. Administrators manage pages, services, projects, home blocks, products, settings and their own account. The release also adds sitemap, robots, canonical addresses and structured data, and it tightens security around sign-in, public forms and CI.

---

# Admin panel
- A panel layout with one navigation map, a top bar and a shared form pattern.
- Corporate screens: about, vision and the legal pages, with limited Markdown per language and a preview.
- Services and projects: image, title and Markdown description in both languages. Projects keep before and after pictures. Both reorder with arrows.
- Home page blocks: the banner, up to six featured products as one ordered list, promo boards and work areas.
- Promo boards have an optional subtitle in both languages.
- Products: search by name or code, a category filter, 24 items per page, and the slug filled in from the Turkish name. A changed slug keeps the old address as a redirect.
- Categories (limit of eight) and catalogs with a PDF up to 4 MB and a cover. The delete dialog names the promo boards that use a catalog.
- Company settings: site name, logo, languages, contact details, service area and social links. The header, footer and contact page read them on every request.
- Account screen for the administrator.
- Unused files: when an image or PDF is replaced or removed, the old file is deleted from the file store after the save succeeds. Demo pictures are never deleted.
- In demo mode the screens are read-only and the server refuses writes.

# Password reset
- A forgot password page and a reset password page, in Turkish and English.
- With SMTP set, the reset link is sent by email. The link points to the localized reset page. The token is valid for 1 hour and works once, and a reset ends every session of the user.
- Without SMTP the pages show a "not available" notice. Recovery is the command `pnpm admin:reset-password`.
- The password needs at least 12 characters.
- Changing the email address takes two steps. The current address must approve the change, and the change ends the user's other sessions.

# SEO
- `sitemap.xml` and `robots.txt` are generated from the settings on each request. Robots closes the whole site unless indexing is on.
- Every page has a canonical address and language alternates (`tr`, `en`, `x-default`).
- Structured data: `WebSite`, `Organization`, `ContactPage` and `BreadcrumbList`.
- The language links follow the current page.
- The site audit checks sitemap, robots, canonical addresses and structured data.

# Visits and statistics
- A small script in the public layout reports each opened page. Crawlers that run no JavaScript are not counted.
- The `visit` table keeps one row per day and shortened address: the day, the address cut to /24 (IPv4) or /48 (IPv6), the country, the city and the number of views. It stores no path, language, referrer or browser string.
- Rows older than 13 months are deleted when a visit is written.
- The Statistics screen shows the last 30 days: visits and page views per day, and the countries. Visitors behind one network count once, so the numbers are an estimate.

# Security
- Sign-in and password routes have explicit limits per client address: sign-in 3 requests per 10 seconds, reset requests 3 per 60 seconds, reset 5 per 60 seconds.
- One account gets at most 3 reset mails per hour, and the answer is the same for a known and an unknown address.
- The contact form has a site-wide limit of 200 messages per day, in addition to the limit per address.
- The visits route accepts only the same origin, a small body and the path of a known public page. It is rate limited.
- The demo account carries a flag that the client can never set. Without `DEMO_MODE=true` the session guard returns no session for it.
- A test fails when a Better Auth upgrade adds an endpoint that is not on the blocked or open list for demo mode.
- A static check fails the build when an admin page, route handler or Server Action has no guard. It covers all route handlers under `src/app` and all script file types.
- CI concurrency groups are keyed on the pull request, and the release rehearsal only fetches the requested ref.

# Fixes
- The letters of the logo tagline are drawn correctly.
- The top bar of the panel lines up with the content edge.
- Panel form texts are consistent and the account form fields are named once.

# Documentation and tests
- The README is rewritten and the guides are up to date.
- A test requires every environment variable to appear in `.env.example`.
- The site audit also signs in with a demo administrator and checks the panel screens.

# Upgrade note
- On a demo site, run `pnpm db:seed:demo` after deploying. It marks the demo user with its flag. Without it, demo sign-in returns no session.

# Known limits
- The live site stays `noindex` until 1.0.0.
- There are no category pages yet.
- There is no blog yet.
- Further performance work comes in later releases.
